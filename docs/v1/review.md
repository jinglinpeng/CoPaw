# Snapshot 设计文档严格 Review

目标文档：`docs/snapshot-design.md`

## 主要问题（按严重级别）

### 1) 完整性校验可被伪造（Critical）

- 文档定义了 `manifest.json` 内的 `file_checksums`，但没有签名机制（如 detached signature / HMAC）。
- 攻击者可同时篡改 `workspace/skills/*` 与 `manifest.json` 的 hash，导入端仍可能“校验通过”。
- 在“不受信任快照导入”场景下，恶意代码注入门槛过低。

### 2) 导入恶意代码的防护不足（Critical）

- 文档仅提“技能代码标记为未审核”，但未定义“默认禁用执行”或“隔离运行”。
- 用户导入后一次常规调用即可触发恶意 skill，风险高。
- 建议：导入的 `skills` 默认 disabled，需显式审核后启用。

### 3) “默认不含敏感数据”与“本地快照默认含 secrets”策略冲突（High）

- 文档存在双重默认语义：一处“默认不含敏感数据”，一处“本地 snapshot 默认包含 secrets”。
- 用户易误判“本地=安全”；被同步到网盘/备份系统后仍可能泄露。
- `0600` 在 Windows 语义不等价，权限策略应按平台定义。

### 4) 一致性锁范围定义不完整（High）

- 仅描述 `AgentRunner` 读写锁，消息入口、cron、副作用任务、外部回调是否都受同一锁约束不清晰。
- “Channel 不暂停，消息可重试”依赖可靠队列与幂等消费，文档未定义。
- 风险：snapshot 前后消息丢失、重复执行、顺序错乱。

### 5) 恢复“原子替换”在跨平台目录级不成立（High）

- Windows 下目录替换常受文件占用影响，“先写临时目录再原子替换”并非总是原子。
- 当前缺少恢复事务状态机（prepare/apply/commit/recover）。
- 崩溃恢复可能进入“备份和目标都半可用”的灰态。

### 6) 加密方案细节缺失，存在实现偏差风险（Medium）

- 仅写“AES-256”，未定义 KDF（Argon2/scrypt/PBKDF2）、随机盐、nonce、AEAD 模式（GCM/ChaCha20-Poly1305）、版本头。
- 缺少密码错误与认证标签校验语义，易出现“解密成功但内容损坏”。

### 7) 跨版本兼容策略过于宽泛（Medium）

- “小版本允许、大版本警告”对 `sessions/*.json`（含运行态 state_dict）不够稳健。
- 建议以 schema migration 与能力协商为准，而非仅靠版本号。

### 8) 资源消耗与 DoS 防护不足（Medium）

- 未定义 zip bomb、超大文件、超深目录、超长路径、海量小文件等限制。
- 导入 API 可能成为 CPU/IO/内存攻击入口。

## 攻击性用户场景（建议重点演练）

- 场景 A：社群分享快照投毒  
用户下载“优秀 Agent 快照”导入，内含恶意 `skills`，导入后触发工具调用。
- 场景 B：同事误传“本地快照”  
误以为“本地快照默认安全”，将含 secrets 的包发送到 IM 或网盘。
- 场景 C：恢复过程断电/进程崩溃  
重启后 workspace 不可启动，且原状态回滚失败。
- 场景 D：高并发消息 + snapshot  
群聊高流量期间执行 snapshot，出现消息丢失/重复回复。
- 场景 E：跨平台迁移  
Windows 导出到 Linux，路径转换后部分绝对路径引用失效，启动时暴雷。
- 场景 F：恶意导入包资源炸弹  
小体积 zip 解压后数十 GB，占满磁盘导致服务不可用。

## 建议测试用例（攻击/破坏性优先）

### 安全类

- 导入包篡改测试：同时修改 `skills` 与 `manifest`，验证能否被拒绝。
- Zip Slip + 链接攻击：`../`、绝对路径、符号链接/硬链接逃逸，验证全部拒绝。
- Zip bomb：高压缩比、海量文件、深层目录，验证配额和提前中止。
- 恶意 skill 默认执行：导入后未经人工确认是否可被调用（预期应禁止）。

### 一致性/并发类

- snapshot 时持续流式响应 + 并发 cron + reload_agent，验证无丢消息、无重复副作用。
- 两个 snapshot 并发 + restore 并发，验证锁语义、错误码一致性、无死锁。
- snapshot 超时中断流式请求后，验证会话状态可恢复且用户可感知。

### 恢复可靠性类

- 恢复中途 kill -9 / 断电模拟，重启后应进入 recover 流程并可回滚。
- 磁盘空间边界测试（1.9x / 2.0x / 2.1x snapshot 大小）验证预检与失败路径。
- 文件占用冲突（Windows 常见）下恢复重试策略与失败补偿。

### 兼容迁移类

- `copaw_version` 前后多个版本矩阵导入，逐项验证 schema migration。
- reme backend 不匹配（chroma -> local）验证降级与重建后的效果阈值。
- `agent_id` 冲突下三分支（覆盖/重命名/取消）行为可预测且可回滚。

### 敏感数据类

- `--include-secrets` 与默认导出对比，确认无敏感字段遗漏（`client_secret`、`api_key`、`auth` 等）。
- Windows 下 secrets 文件 ACL 验证（不能只测 `0600`）。
- 密码错误、密码正确但包损坏、算法版本升级后的兼容解密测试。

## 必须补齐的设计空白（Gate）

- 快照真实性与来源可信度如何保证（签名/HMAC）？
- 导入的 `skills` 是否默认禁用？审核流程与状态存储位置是什么？
- 锁的精确定义：覆盖哪些入口、组件与顺序约束？
- 恢复事务状态机与崩溃恢复流程图是否明确？
- 导入资源限制阈值（文件数、单文件大小、解压总量、路径长度）是多少？

## 用户使用场景风险（产品/运营视角）

### 1) 用户认知偏差类

- 用户将“恢复快照”理解为“撤销所有已发生行为”，但外部副作用（发送消息、调用第三方 API、创建工单）不会回滚。
- 用户将“本地快照”理解为“绝对安全”，忽略同步盘、备份系统、IM 传输带来的泄露路径。
- 用户将“导入成功”理解为“可立即运行”，忽略依赖缺失、Token 失效、MCP 不可达等后置失败。

### 2) 误操作与高压场景类

- `agent_id` 冲突时误选“覆盖”，导致当前可用配置被替换。
- 业务高峰期执行 snapshot/restore，造成排队、超时、卡顿，用户感知为服务不稳定。
- 大文件导入导出缺乏明确进度反馈时，用户重复点击触发并发操作与状态竞争。

### 3) 跨团队协作类

- 团队通过 IM/网盘共享快照时，未统一加密策略与密码交接流程，导致“可分享但不可恢复”或“明文泄露”。
- 成员导入来源不明快照，默认信任第三方内容，触发供应链式风险（恶意 skills / 配置投毒）。

### 4) 跨环境迁移类

- Windows -> Linux 或反向迁移时，路径、权限、脚本执行环境差异导致“导入成功但运行失败”。
- 旧版本快照迁移到新版本时，运行态会话状态不兼容，问题在实际对话阶段才暴露。

## 面向用户体验的补强建议（可落地）

- 在创建/恢复/导入流程中，强制展示“恢复不回滚外部副作用”的确认提示。
- 将“导入成功”拆分为“导入成功 + 可运行性检查结果（依赖/MCP/渠道认证）”两阶段反馈。
- `agent_id` 冲突时默认选项改为“重命名”，并将“覆盖”设为二次确认。
- 对高耗时任务提供进度、预计剩余时间、可取消能力，并禁止重复触发同类任务。
- 对含 secrets 的导出包添加显著标识和二次确认；默认推荐加密导出。
- 导入第三方快照后默认禁用 skills，要求用户手动审核并启用。
